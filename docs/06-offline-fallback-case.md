# 案例：设备换了个网络环境就「傻了」

> 一次真实排查的全记录。这篇的价值不在修了什么，而在**排查手法**：
> 「在新环境下不工作」类问题，用「逐层问谁在等谁」五步定位；
> 以及两个复用组件/状态判定上的通用陷阱。

---

## 一、现象

设备在公司配好网（NVS 里存着公司 SSID），用户带回家：

> 「设备在其它网络环境下不懂识别当前网络环境不对」

实际行为：开机后**永远停在引导屏转圈**——「正在连接网络…」+ 保存的 SSID + 进度环，不超时、不报错、不开配网热点。用户能做的只有看着它转。

---

## 二、排查：把链路画出来，逐层问「谁在等谁」

这类问题的排查法：**把数据流经的每一级画出来，对每一级问同一个问题——「它在等谁？对方一定会应答吗？」**

| 级 | 行为 | 它在等谁 | 对方会应答吗 |
|---|---|---|---|
| ① `dada_net_init()` | NVS 有凭证 → 置 CONNECTING → `StartStation()`，非阻塞 | 等下层连上 | ✅ 会（连上/连不上都有事件） |
| ② `WifiStation` 后台循环 | 扫描 → 在结果里找保存的 SSID → **家里没有** → 退避 10s→20s→40s…封顶 5min → 再扫 | 等附近出现那个 SSID | ❌ **永远不会** |
| ③ 引导屏 UI | 只认 CONNECTED 才离开；CONNECTING 就永远停留 | 等 ① 变 CONNECTED | ❌ 同上 |

**根因定案：不是 bug，是「无兜底设计」——每一级都在等下一级，而第二级永远等不到。**

关键证据在第二级：扫不到已保存 SSID 时，上游组件的行为是**无限重扫、永不放弃、也绝不开配网热点**。这是组件的设计（它假设调用方会管超时），但我们引入组件时只抄了「连接」部分，没抄「等待+兜底」的约定。

---

## 三、修复：兜底策略必须由人拍板

AI 列了三个选项，用户拍板第二个：

| 选项 | 行为 | 评价 |
|---|---|---|
| A. 超时转配网 AP | 15s 连不上 → 自动开配网热点 | 改动最小，但用户只是「换个环境用用」时被迫重新配网，体验重 |
| **B. 超时进主页离线态** ✅ | 15s → 提示「附近没有已保存的 Wi-Fi」2s → 进主页 | **断网状态如实可见**（信号 0 格、时间 `--:--`），且后台扫描不停 |
| C. 直接跳过进主页 | 不提示直接进 | 用户根本不知道发生了什么 |

选 B 的关键收益：**后台 STA 扫描循环不停止**。用户在家打开手机热点后，最迟 5 分钟内设备自动连上，SNTP 对时、天气刷新全部自愈——**不需要任何人工干预**。兜底不是「放弃连接」，是「换个地方等」。

实现要点：

- CONNECTING 停留超 15s → 结论帧（进度环停转、提示文案、SSID 保留供核对：「哦，这个设备里存的不是我家的网」）→ 2s 后进主页；
- **CONFIG 态（用户主动配网中）永不超时**——兜底只针对「自动连接」，不针对「用户正在操作」；
- 超时判定的代码位置有讲究：放在 CONNECTED 判断**之后**，保证「连上了」永远优先于「超时了」，临界竞态不误判。

---

## 四、连带挖出的坑：假时间（比主问题更隐蔽）

排查中发现主页的时间显示判定是：

```c
synced = (time(NULL) >= 1700000000);   /* 时钟过了 2023 年阈值就算「已对时」 */
```

**这个判定在离线态下会撒谎。** ESP32 的 RTC 域硬复位不断电，系统时钟带着上次运行的值起来——阈值恒真，`synced` 恒真。于是离线主页会把**上次的旧时间当真显示**，用户根本看不出设备没联网。

修法：sticky 标志——SNTP 同步回调里置位、本次开机永不清除：

```c
synced = (time(NULL) >= DADA_EPOCH_SYNCED) && dada_net_time_synced();
```

为什么不用「读 SNTP 模块的实时状态」：同步完成后状态位会复位去等下一轮，读它会让界面每过一个周期就闪回一次 `--:--`。**sticky 标志单调、无抖动。**

> **通用教训**：
> ① 「系统时钟看起来对」≠「对过时」——带保持域的 RTC 会让旧值无限期冒充现值；
> ② 「是否同步过」这种一次性事件，用 sticky 标志，不要用阈值推断，更不要读会复位的实时状态。

## 五、方法论沉淀

### 5.1 「新环境下不工作」类问题五步法

```
1. 描述用户实际操作（换环境 → 开机 → 看到什么）
2. 画状态机/数据流，标出每一级「在等谁」
3. 对每一级问：对方一定会应答吗？——找到永远等不到的那一环
4. 问上游组件：「这个场景你原来的设计里谁管？」(WaitForConnected 一直在，没人用)
5. 兜底策略列选项，用户拍板；AI 不自行决定产品行为
```

### 5.2 复用组件要连「约定」一起抄

`esp-wifi-connect` 提供了 `WaitForConnected(timeout_ms)`——**这个函数的存在本身就是契约**：调用方应该等一个有界时间，超时后自己决定怎么办。我们只抄了连接部分，把等待和兜底漏了。

> **看到组件里有个没人调用的 `WaitForXxx(timeout)`，先问「原来的调用方在哪」——答案就是你没抄的那部分设计。**

### 5.3 「无兜底」是设计问题，不是 bug

三个单看都「没写错」的模块，组起来成了一个卡死的系统。**每一级都假设别人会兜底，就等于没人兜底。** 画链路时专门问一句：「这条链的尽头断了，谁负责收尾？」

## 六、本节 Checklist

- [ ] 排查「新环境不工作」：画状态机 → 逐层问「在等谁」→ 找永远等不到的那环
- [ ] 兜底策略**列选项给用户拍板**，AI 不自行决定产品行为
- [ ] 兜底不能停掉自愈通道（后台重试/扫描继续），「换个地方等」优于「放弃」
- [ ] 用户主动操作中的状态（配网中/编辑中）不参与自动超时
- [ ] 超时判定放在「成功判定」之后，临界竞态不误判
- [ ] 复用组件时，把没人调的 `WaitForXxx(timeout)` 当作契约线索查原设计
- [ ] 「已同步/已连接」类状态禁用阈值推断（RTC 保持域会说谎），用 sticky 标志
- [ ] 每条链专门问一次：「尽头断了谁收尾？」
