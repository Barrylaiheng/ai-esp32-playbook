# 09 · 列表/网格虚拟化：复用粒度决定观感

> 场景：ESP32-S3 + LVGL 的相册网格，2 行 × 3 列可见、对象池 9 格。
> 用户原话：「平滑拖动的时候渲染速度很慢，体感有欠缺。」
> 结论：**不是慢，是每次滚过一行整屏被拆掉重建。**

## 结论（TL;DR）

**列表项的身份必须绑定「视口坐标」，不能绑定「数据下标」。**

绑错了的后果不是「慢一点」，是**整屏闪空**：滚动跨过一行时，池里所有槽的
下标同步平移，每个槽都判定为「换了另一条数据」→ 全部释放、全部重建。
用户看到的是「旧图消失 → 空白 → 一张张重新长出来」。

本案例的实测：跨一行解绑 **9 格 → 0 格**，主观评分 60 → 80。

## 症状与误判

| 现象 | 第一直觉 | 实际 |
|---|---|---|
| 拖动时图不跟手 | 解码太慢 | 拖动中**预算被清零，一张都不解** |
| 松手后图一张张浮出 | 解码慢 | 每张都在重读重解（因为全被拆了） |
| 跨行瞬间整屏变白 | 内存不够 | 池里的 9 格全被 unload |

三条现象都指向「慢」，但真因只有一条：**复用粒度错了**。

## 根因：槽 ↔ 数据的映射被写成了绝对下标

常见的池化实现是这样写的（错的）：

```c
/* 第 k 个槽 永远显示 第 (base*3 + k) 张照片 */
slot_bind(k, base * 3 + k);
```

看起来没问题——它确实「算对了」。问题在于**当 `base` 变化时，几乎每个槽的
目标下标都变了**：

```
滚动前 base=0 → 槽 0..8 显示照片 0,1,2,3,4,5,6,7,8
滚动后 base=1 → 槽 0..8 显示照片 3,4,5,6,7,8,9,10,11
                  ↑ 9 个槽里 8 个的下标变了
```

于是在「槽的 idx != 目标 idx 就释放重建」的逻辑下，**一次跨行 = 整池重建**。
明明只需要换掉滚出去/滚进来的那一行（3 格），其余 6 格只是**在屏幕上挪了 134px**。

这就是 RecyclerView 的 `ViewHolder` 与「按 position 取数据」的区别：
Android 的 item 位置是**滚动偏移的函数**，滚出屏幕才回收；
把槽钉在绝对下标上，等于放弃了复用。

## 修法：先搬图，再绑定

在进入绑定循环**之前**，按行整体搬一次池内容：

```c
if (base != prev_base) pool_shift(base - prev_base);   /* 必须在循环之前 */

for (k = 0; k < POOL_MAX; k++) slot_bind(k, base * 3 + k);
```

`pool_shift(d)` 只搬 **dsc + 缓冲指针**（3 次结构体拷贝 + 3 次
`lv_image_set_src`），不搬像素，亚毫秒级：

```c
static void pool_move(int dst, int src) {
    /* 先断开源的引用再交接缓冲：
       dst 之后会指向同一块内存，若源仍引用，源被重绑时会误用一块
       已经换主的内存 —— 这类 UAF 在 LCD/图像项目里是常客。 */
    if (s->buf && s->cell && d->cell) {
        lv_image_set_src(s->cell, NULL);
        d->dsc = s->dsc;
        d->buf = s->buf;
        s->buf = NULL;
        lv_image_set_src(d->cell, &d->dsc);
    }
}
```

搬完之后，下面 9 次 `slot_bind` 全部命中「已绑对」分支，**只有滚入的那 3 格是空的**。

## 两个必须注意的实现细节

### 1. 池被搬走后，「已绑对」分支不能提前 return

原实现的短路是这样的：

```c
if (pc->idx == idx) {
    if (idx >= 0 && do_load && allow_full) grid_cell_load(pc, idx, true);
    return;                       /* ← 位置、描边、勾选框全都不再更新 */
}
```

搬到新位置后 idx 确实已经对了，但**对象在屏幕上的坐标还是旧的**。
必须抽出幂等的 `cell_sync()`，让「已绑对」也走一遍位置/描边/角标/勾选框的复位。

### 2. 绝对坐标必须与容器滚动做补偿

这一点最容易漏，漏了就是**图叠在一起**：

- cell 的位置是按数据算的绝对坐标：`y = (idx / 3) * ROW_H`
- 而容器同时滚动了 `+ROW_H`
- 两者**恰好抵消**，屏幕上位置才不动 → 视觉无缝

所以 `pool_shift` 搬完图之后，`cell_sync` 必须把 `+ROW_H` 补上。补对了看不出变化，
补错了立刻错位——这是个**没有中间态**的检查点。

## 怎么证明改对了（不靠肉眼）

留一个同固件 A/B 开关，比跨两次编译对比可靠得多（排除环境差异）：

```c
static bool s_shift_on = true;          /* 串口命令可在运行时切 */
static int  s_unl_n;                    /* 每次 unload 自增，跨行后打印 */
```

实测（同一台设备、同一份数据、同一次上电）：

| 开关 | 跨行 | 解绑格数 |
|---|---|---|
| 开 | 0→1 / 1→2 / 1→3 / 3→1 | **0** |
| 关 | 2→1 | **9** |

**这里有个比数字更有价值的推论**：`unload = 0` 本身就证明 9 个槽的下标映射全对——
只要有一个槽搬错，`slot_bind` 就会判定「换了数据」而解绑，计数必然大于 0。
**所以「图对不对」不需要另外找视觉证据，计数就是断言。**

配套还验了两件：8 次连续跨行（含 ±2）无崩溃；PSRAM 滚 6 次后比基准**多 4KB**
（free/alloc 平衡，无泄漏）。第三次读数少 108KB 是「首屏只解 2 张 vs 最终解满 9 张」
的正常差，不是泄漏——**基准点选对，才不会被这种正常波动吓到**。

## 边界必须诚实：这条修完还剩什么

| 已解决 | 未解决 |
|---|---|
| 跨行不再整屏闪空，旧图跟着手指走 | **滚入的新行在拖动过程中仍是空的** |
| 末屏不满池、首屏各种 base 都覆盖 | 拖动中 `budget = 0`（一张不解，避免单张 35ms 卡住跟手） |
| 选择模式勾选框随槽走（`cell_sync` 统一复位） | 松手后按 20ms/tick 补解，3 张约 100~150ms 填满 |

要把最后那点也补掉，得上**内存缓存**（144×108 RGB565 = 31KB/张，缓存 12~18 张
= 372~558KB PSRAM）。但那是另一个成本台阶，先让用户拿到「80 分」，再决定要不要付。

> 这条经验值得单独记：**「改完能拿多少分」要事先说清楚，别把 80 分说成 100 分。**
> 用户摸着设备给 80 分，就到此为止；剩下 20 分的性价比要他自己判断。
