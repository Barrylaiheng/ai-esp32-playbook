# 黄金图回归门：让「改 A 弄坏 B」当场现形

> 主文第 6 节的展开。截图自检回答「**这一轮改得对不对**」，回归门回答「**有没有把对的改坏**」。
> 后者是 LVGL 官方 CI 用了很多年的做法（`ref_imgs/` 参考图逐像素比对），
> 这篇记录我把它搬进 AI 工作流的过程，以及**门第一次运行就误报、第二次差点漏报**的两个坑。

---

## 一、为什么需要它（一个真实场景）

AI 改 UI 的闭环是「改 → 截图 → AI 看 → 再改」。这个闭环有个盲区：

> **它只检查 AI 这次「想看」的那一屏。**

真实事故：AI 改引导屏文案，模拟器截图上新文案全是**方框字**（字体子集没覆盖新字符）。
如果当时有回归门，这一屏和参考图必然不同 → 当场 FAIL。而实际上这个问题是烧录到真机后才发现的。

**回归门 = 把「每一屏都和上次比」变成默认动作**，不依赖 AI 记得去看。

---

## 二、实现：参考图 + 逐像素比对 + 独立退出码

```
preview/refs/<screen>.png      ← 黄金参考图（入库）
preview/refs/tolerance.json    ← 各屏容忍度（默认 0）
tools/check_refs.py            ← 比对器
tools/iterate.ps1              ← 一轮：编译模拟器 + N 屏截图 + 像素自检 + 回归门
```

三处关键设计：

**1. 独立退出码。** 迭代脚本 exit 0=全绿 / 2=有屏渲染异常 / **3=回归**。AI 拿到退出码就能自己分支，不需要人看输出。

**2. 显式更新语义。** 改 UI 是**有意变更**，所以更新参考图必须显式传 `-UpdateRefs`——和 LVGL 官方 CI 的 `--update-image` 同构。防止「为了绿灯偷偷换参考图」。

**3. 突变测试验收门本身。** 门装完必须验证它**真的会叫**：故意把某屏参考图涂坏一块（模拟字体缺字），门必须报 FAIL + exit 3。**一个没被突变测试验证过的门，等于没有门。**

---

## 三、意外收获：`--shot` 是完全确定性渲染

建档后第二轮复跑，预期是「静态屏 identical、动效屏有差异」（呼吸/转环动画嘛）——结果**五屏全部 identical**。

原因：模拟器的 `--shot` 模式跑的是虚拟 tick（`lv_tick_inc` + `lv_timer_handler` 手动步进），所有动画都冻结在同一帧。**这比预期好得多：意味着动效屏也可以纳入零容忍回归。**

唯一漏掉的环境输入是时钟——于是有了下面第四个坑。

---

## 四、坑一：PIL 的 `getbbox()` 在 RGBA 差值图上会漏报

第一版比对逻辑：

```python
d = ImageChops.difference(a, b)
if d.getbbox() is None:
    return "identical"          # ← 错！这里漏报了 3146 个像素的差异
```

**现象**：手工 `getpixel` 明明不同（一个白块一个暗色），门却报 identical。突变测试当场失败——但失败得很有价值。

**根因**：RGBA 差值图上 alpha 通道全 255（差值全 0），`getbbox()` 在 alpha 全零时返回 `None`，而 RGB 通道差了 3146 个像素它根本看不见。

**修法**：逐波段掩码精确计数——

```python
mask = ImageChops.difference(a.convert("RGB"), b.convert("RGB")).convert("L")
diff_px = sum(1 for v in mask.getdata() if v > 0)   # 任何非零差异都算
```

> **通用教训**：任何「用 getbbox/直方图求和判断两张图是否相同」的代码，在带 alpha 的图像上都要重新验证。
> 工具的返回值语义（None=「这个通道全零」）和你的语义（None=「两张图相同」）**不是一回事**。
> 这类「检测器本身有 bug」的问题，只有突变测试能逮住。

---

## 五、坑二：参考图会被「活时钟」熬过期

门跑了两周都没事，某天突然 FAIL：home 屏 10413 像素差异、settings 368 像素。

**第一反应是「谁把 UI 改坏了」——但这次真的没有。** 差异全部来自时间显示：宿主时钟在走，home 大钟数字每分钟变、信息桌面「X月X日 · 周X」每天变。**参考图天然 staleness，和代码无关。**

排查过程本身值得记：先 diff 两版代码（无相关改动）→ 再看差异像素的**位置**（恰好是时钟数字区域）→ 才定位到时间源。

**修法：截图模式冻结整个时钟。**

```c
/* sim_clock.c：--shot 默认冻结到固定时刻，交互预览仍取真实时间 */
void sim_clock_freeze(bool on);
```

- `--shot`（AI 自检/参考图比对）→ 冻结到固定时刻（如 2026-01-15 10:08:00，秒归零）
- 交互预览模式（SDL 窗口）→ 不冻，保持「所见即真机所见」
- 两个逃生口：`-live` 显式关冻结看真实时间；`-time HH:MM` 在冻结基准上注入时分

冻结后 home 容忍度从 0.5% **收紧为 0**——全屏确定性渲染，没有借口了。

> **通用教训（这篇最重要的一条）**：
> **参考图/快照类测试的第一嫌疑人，永远是「时间源没冻结」，不是被测代码。**
> 而且根因是注入体系不全——电量、信号、网络状态早就能注入，
> **时钟是最后一个漏网的环境输入**。列注入清单时按「这个屏上有多少个数据来自外部世界」逐个过一遍。

## 六、完整落地清单

```
[ ] 参考图目录入库（preview/refs/），容忍度表默认全 0
[ ] 比对器：逐波段掩码计数，禁用 getbbox 判「相同」
[ ] 迭代脚本接门，独立退出码（3=回归），-UpdateRefs 显式更新语义
[ ] 突变测试：涂坏一屏参考图，门必须 FAIL —— 没做过这个的门不算门
[ ] 截图模式冻结全部环境输入：时钟/电量/信号/网络态……
[ ] 交互预览保留真实数据（-live），别为了测试把产品预览也变假
[ ] 参考图随有意变更重拍，提交信息里写清为什么变
```
