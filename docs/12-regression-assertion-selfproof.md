# 12 · 回归断言必须先自证：一条永远为真的断言等于没有断言

> 场景：给相册的滚动行为补离线回归。此前 21 项全是**静态像素检查**
> （格子有没有图、顶栏对不对、按钮位置），一条滚动行为都没覆盖。
> 补完 44 项后回头看，最值钱的不是新增了多少条断言，而是发现
> **新写的三条断言里，有两条一开始是错的**——功能没问题，是断言在骗人。

## 结论（TL;DR）

**① 断言要证明的是「过程没走错」，不只是「结果看起来对」。**
像素检查只能证明「现在屏幕上有图」。而「图被拆掉、重建一帧后又有了」同样通过像素检查——
但中间那一下整屏闪空，正是用户抱怨的东西。**结果与过程的观感可以差一个数量级。**

**② 一条永远为真的断言等于没有断言。**
写完断言必须做**反向验证**：人为把功能关掉（A/B 开关），
确认断言**真的会失败**。两种状态都读到通过 → 这条断言是摆设。

**③ 断言本身也会写错，而且错的方向很阴险：功能对了，断言报失败。**
今晚两条新断言第一版都误报——一条取错了日志里的数字位置，一条算错了勾选目标的位置。
如果不做反向验证，这些错误会伪装成「功能有 bug」，把人带去改正确的代码。

## 症状与误判

| 现象 | 第一直觉 | 实际 |
|---|---|---|
| 回归全绿，用户仍在抱怨 | 用户主观 / 没复现 | 断言只查静态结果，没覆盖行为路径 |
| 像素检查通过 | 「图没被拆掉」 | 也可能「拆了又重建」，中间闪空没被采到 |
| 新断言 FAIL | 功能有 bug，去改代码 | 断言写错了：数字取错位 / 期望值算错 |
| A/B 两种状态断言都通过 | 两种实现都对 | 断言恒为真，是摆设 |

## 案例 A：像素断言证明不了「没被拆掉」

滚动跨行时，槽位按绝对下标绑定，一跨行 9 个槽全部重绑 → 全部 `unload`（释放缓冲 +
断开 `src`）→ 整屏闪空，松手后再一张张长回来。修完（见第 09 篇）后要把这条经验固化成回归。

第一反应是加像素断言：滚完一行，截屏，检查网格区有没有内容。
**这条断言在 bug 版本里也会通过**——因为滚完补解已经完成，屏上当然有图。
它采不到「中间那 300ms 空屏」。

真正的证据在日志里：

```
[albscroll] 行 0 -> 1：解绑 0 格（改前必为 9）
```

**解绑格数 = 0 才是「图是搬过去的，不是拆了重建」**。这个数字为 9 时，
像素断言照样绿，但用户看到的是整屏闪空。

> 推论：**当 bug 的本质是「过程错误」时，结果态断言天然抓不到它。**
> 要么让代码在过程里留下可断言的痕迹（埋点计数），要么在过程的中间态采样。
> 前者便宜得多。

## 案例 B：断言里的数字不止一个

日志格式：

```c
printf("[albscroll] 行 %d -> %d：解绑 %d 格（改前必为 %d）\n",
       prev_base, base, s_unl_n - unl0, POOL_MAX);
```

一行四个数字：`prev_base`、`base`、**解绑数**、`POOL_MAX`（说明文字里的 9）。

第一版解析写成了「取最后一个数字」：

```python
nums = [int(x) for x in re.findall(r"\d+", line)]
unl = nums[-1]        # ❌ 永远拿到末尾说明里的 9
```

于是正确实现（解绑 0 格）被报成「解绑 9 格」，**回归 FAIL，功能其实完全正常**。

修法：按语义位置取第三个，并且显式注释说明为什么末尾那个不能取：

```python
nums = [int(x) for x in re.findall(r"\d+", line)]
# [prev_base, base, unload, POOL_MAX] — 第 3 个才是解绑数，
# 末尾那个是「改前必为 9」的说明文字（已经踩过一次）
unl = nums[2]
```

> 教训：**日志是给人读的，正则不读语义。** 在断言里解析日志，
> 要么给埋点单独输出一行只有目标数字的机器可读行，
> 要么按位置取并在旁边写清每个位置是什么。别用「最后一个数字」这种偷懒写法。

## 案例 C：期望值算错，也会伪装成功能 bug

选择模式下滚动的断言：勾选两张照片，滚动后检查勾选标记还在不在（网格区橙色像素数）。

第一版勾的是 idx 3 和 5。滚 268px 后，视口里可见的是 idx 6 起——**这两张已经滚出屏幕了**。
橙色像素 0 是正确结果，不是「标记丢了」。

修法不是改代码，是改断言的**输入**：勾滚动后才进视口的 idx 6/9，
验证「勾的时候看不见、滚回来必须带着勾」——这恰好是更容易出错的场景
（对象池复用时勾选状态必须跟着照片走，不跟着槽对象走）。

> 教训：**期望值要按「断言发生的那一刻」算，不是按「设置输入的那一刻」算。**
> 中间隔了滚动、切屏、异步补解，状态早就不一样了。

## 修法：把反向验证固化成脚本自检

写完断言后加一个自检模式，人为制造「老行为」，确认断言会失败：

```
移位开（新逻辑）：解绑 0 格  → 断言期望 0 ✓
移位关（老行为）：解绑 9 格  → 断言期望 0 ✗  ← 必须失败
```

实现上给被测代码加一个只用于测试的开关（本项目是 `DADA_SIM_SHIFT_OFF=1`），
自检模式跑两次，如果两次都读到 0（或两次都读到非 0），说明断言区分不了新旧行为，直接 FAIL：

```python
if ok_n == 0 and bad_n == 9:
    print("[self-test] PASS：断言能区分新旧行为")
    return 0
# 任何一个数字不对 → 断言本身有问题
```

固化成 `--self-test-scroll` 后，以后每次改回归脚本都先跑一遍自检，再跑完整回归。

> **为什么这一步值钱**：它把「断言可信」从「我觉得写对了」变成「机器证明过」。
> 一次投入，之后所有断言改动都受保护。

## 铁律

- [ ] **行为类 bug 不能只靠结果态截图断言**——「拆了又重建」和「没拆」结果一样，
  过程不一样。让代码在过程里留下可断言的计数（如 unload 次数）。
- [ ] **写完断言立刻做反向验证**：关掉功能，断言必须失败。两种状态都通过 = 断言是摆设。
- [ ] **一条永远为真的断言比没有断言更坏**：它占用维护成本，还给人虚假的安全感。
- [ ] **断言 FAIL 时先怀疑断言**，尤其是新写的：数字取错位置、期望值算错时刻、
  采样时机提前/滞后。确认断言可信之后再去改功能代码。
- [ ] **解析日志别用「最后一个数字」**：按语义位置取 + 注释每个位置是什么，
  或者给埋点单独输出机器可读的一行。
- [ ] **自检本身要检查两个方向**：正向通过 + 反向失败，缺一不可。
  只验「正向通过」等于没验。

## 边界（诚实记录）

- 反向验证需要一个测试开关。**开关本身是产品代码的额外分支**，
  要确保它只在测试构建里可达、默认关闭，别让它进入用户路径。
- 埋点计数（`s_unl_n` 这类）会略微侵入产品代码。本项目的取舍是保留埋点、
  但只在异常时打印（0 条目 / 超阈值才输出），正常运行时无噪声。
- 断言能区分新旧行为，**不代表覆盖了所有错法**。它能证明「移位这段逻辑对」，
  证明不了「图的内容对」——后者仍需像素/视觉检查。两类断言互补，不能互相替代。
