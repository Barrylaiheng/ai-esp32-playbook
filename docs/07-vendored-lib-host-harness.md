# 07 · 复用第三方 C 库：先写 30 行宿主端复现，再进产品

> 场景：ESP32 相机/相册功能需要 JPEG→RGB565 解码，选了 LVGL 自带的 tjpgd
>（ChaN TJpgDec R0.03）。「集成 → 真机调试 → 怀疑人生」的经典弯路，
> 用「宿主端最小复现」30 分钟走完。

## 结论（TL;DR）

1. **任何「回调契约 + 配置宏」型 C 库，接入前先在 PC 上写 30~50 行 harness
   直接驱动它**，用真实形态的输入过一遍主路径。嵌入式构建慢（增量 35s 起），
   宿主端 gcc 一轮 <2s，而且能 printf 追调用序列。
2. 本次 tjpgd 连踩三坑，全部只有 harness 能定位：

| 坑 | 症状 | 根因 |
|---|---|---|
| infunc `buff=NULL` 语义 | APP0/EXIF 段之后 `jd_prepare` 报 `JDR_INP(2)`，纯色图正常、带 JFIF 头的图全灭 | `NULL` 是**跳段**约定：丢弃 nbyte 字节并返回实丢数；想当然写成「返回剩余字节数」就把流读歪了 |
| `jd_decomp` 第三参 | 传 4/8 直接 `JDR_PAR(5)` | 参数是 **log2 档位 0..3**（0=1/1, 1=1/2…），不是分母 |
| scale 输出损坏 | 1/1 完美、1/2 起高频细节横向拖影（FASTDECODE 0/1 皆然） | R0.03 的 scale 输出路径缺陷，不值得 vendor 内修 |

3. **终局方案：恒 1/1 解码，缩放交给显示端（LVGL STRETCH/CONTAIN）**。
   代价是解码缓冲按源尺寸给（VGA=600KB，PSRAM 无压力）——
   「省内存的 scale」是伪优化，坏一像素全盘皆输。

## 方法模板（可搬走）

```
1. 隔离三变量：数据 / 代码 / 配置
   - 纯色 JPEG（PIL 一行生成）→ 过 → 解码器主路径没坏
   - 真实形态 JPEG → 挂 → 换输入再试，锁定「内容相关还是路径相关」
2. 给回调加 printf 追调用序列（infunc 收到的 n/avail/返回值）
   —— 契约类 bug 在调用序列里肉眼可见
3. 对照库源码确认语义（grep 调用点，读注释），别按直觉猜
4. 定论后回产品代码，真机只做「再看一眼」
```

## 附：本次 harness 三板斧

- `tjtrace.c`：infunc 逐次打印 → 一次看出 `NULL` 调用返回值没推进流；
- 每档 scale **独立会话**测试（`jd_decomp` 消费码流，同会话重调必报错，
  会把「档位不可用」误判成「码流坏了」）；
- 解码输出 dump 成 RGB565 raw，Python 十行转 PNG 肉眼比对——
  「能跑」和「像素正确」是两回事。

## 与本项目其它篇的关系

- 坑 1/2 属于「契约未读就写」；坑 3 属于「编译通过 ≠ 功能正确」——
  都被第 05 篇的黄金图回归门在 UI 端兜住（截图从碎条纹变成正确画面，
  content 像素数 0→44k 一目了然），但**定位**靠的是宿主 harness。
  两件套：模拟器回归管「有没有坏」，harness 管「为什么坏」。
