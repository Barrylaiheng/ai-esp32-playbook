# 组件复用纪律：许可证、可分性、隐藏依赖

> 主文第 7 节的展开。AI 让「找一个现成组件来用」变得极其容易，但它**不会替你考虑法律风险和技术债**。

---

## 一、动手前：先查许可证（20 分钟省下重写产品）

我要做 Wi-Fi 配网 + 城市选择。可选路径有两条：复用一个成熟组件，或自己写。

**第一步不是看代码，是看许可证。**

| 对象 | 许可证 | 可否二创 / 商用 / 闭源 |
|---|---|---|
| 某开源语音助手固件 | MIT | ✅ |
| `78/esp-wifi-connect` 组件 | MIT | ✅ |
| 同类开源硬件固件 | MIT | ✅ |
| 某电商品牌整机固件 | **未开源** | ❌ 只能参考思路，**无代码可抄** |

**结论**：目标组件全部 MIT，可以二创、商用、闭源，义务只有一个——附 `THIRD_PARTY_NOTICES.md` 保留版权声明。

### 三个必须分清的概念

| 说法 | 实际含义 |
|---|---|
| 「它开源了」 | 你能**看**代码 |
| 「它是 MIT」 | 你能**用**代码（含商用闭源），需保留声明 |
| 「它整机固件没开源」 | 只能参考**思路**，不能复制代码 |

> **其中最容易踩的**：一个设备可能「某个子功能开源、整机固件不开源」。
> 如果你只看到仓库里有代码，就以为整个产品都能抄，那是灾难。

## 二、再查：组件的架构可分性

**原则：逻辑可以复用，UI 必须回到自己的品牌语言。**

但能不能做到，取决于组件的架构。以 `esp-wifi-connect` 为例：

| 层 | 内容 | 是否要改 |
|---|---|---|
| 逻辑层 | SSID 管理 / STA 连接 / DNS 服务器 / 配网状态机 | ✅ 直接复用 |
| 展示层 | 内嵌的 HTML 页面（占总代码量 **55%**） | ❌ 换成自己的 VI |

它的 HTML 是通过构建系统**嵌入式**打进固件的（`EMBED_TXTFILES`），所以替换只需要换那几个 HTML 文件——逻辑一行不用碰。

**决策方法**：

```
先找组件里"逻辑 / 展示"的缝在哪
  ├─ 缝很清晰（如 HTML 与 C 分离）→ 复用逻辑，重做展示   ← 成本最低
  └─ 缝糊在一起（UI 字符串散落在逻辑里）→ 自己写反而更干净
```

> **别为了复用而复用。** 一个 UI 与逻辑纠缠不清的组件，改起来比自己写还慢。

## 三、复用前先读懂它的行为（不是读 API，是读行为）

组件文档里写的 API 是「怎么调用」；**你真正需要知道的是它「会自己干什么」**。

`esp-wifi-connect` 的行为调研结论（这些都没写在我最初看的 README 里）：

| 行为 | 细节 | 对我意味着什么 |
|---|---|---|
| **多 Wi-Fi 记忆** | 自带 10 组上限；满了淘汰**最旧**的；新配的排最前（= 优先级最高） | 用户「走到哪配到哪」是天然的，产品上不用自己实现 |
| 同 SSID 重配 | 直接覆盖密码 | 用户改密码不需要先删记录 |
| 自动切换 | v2.0+ 会自动切到最佳网络；v3.3+ 存 channel 加速扫描 | 不用自己写重连逻辑 |
| 无凭证行为 | 等约 1.5 秒 → 自动进配网 | 我需要为它准备「配网第 0 态」的 UI |
| 连接失败 | 60 秒连不上自动进配网 | 同上 |

**方法**：让 AI 去读**源码**而不是 README，用表格把「它会自己做什么」逐条列出来。
这张表直接决定了你要写多少自己的逻辑。

## 四、离线化（vendor）与隐藏依赖坑

为了构建可复现，我选择把组件 **vendor** 进 `components/`（而不是走组件管理器联网拉取）。

### 4.1 标准动作

```
组件包解压到 components/<name>/
删除 idf_component.yml        ← 为了彻底离线
删除 .gitignore / sbom 等无关文件
```

### 4.2 坑：删掉 `idf_component.yml` 之后，依赖链断了

删完立刻编译失败：

```
fatal error: cJSON.h: No such file or directory
```

**根因**：上游的 `CMakeLists.txt` 里**根本没有声明 `cjson`**——它是靠 `idf_component.yml` **自动注入**的。yml 一删，注入也就没了。

**修法**：手动在组件的 `CMakeLists.txt` 里补上：

```cmake
# NOTE: cjson is NOT declared in the upstream CMakeLists.txt.
# It is injected by idf_component.yml. Since we vendored the component
# and removed that file for full offline builds, we must declare it here.
if(IDF_VERSION_MAJOR GREATER_EQUAL 6)
    idf_component_register(... REQUIRES cjson ...)
endif()
```

### 4.3 通用教训

> **`idf_component.yml` 不只是"声明依赖给你看"，它真的在做依赖注入。**
> **离线化的代价就是：你必须自己补上它注入过的东西。**

**离线化检查清单**：

- [ ] `idf_component.yml` 里 `dependencies` 的每一项，是否都已在 `CMakeLists.txt` 的 `REQUIRES`/`PRIV_REQUIRES` 里出现
- [ ] 是否还有构建期脚本（如资源生成）依赖网络
- [ ] 是否保留了原始的版本号与来源信息（写进 `third_party/README.md`）

### 4.4 顺带：把原始包留档

`third_party/` 里保留原始组件包（zip），并记录**来源 URL / 版本 / 校验值 / 许可证义务**。
将来上游修复了 bug，你才知道该去哪里更新。

## 五、验证复用是否真的生效（一个容易误判的点）

接入组件后构建通过，但产物大小几乎没变——**很容易误判为「组件根本没被编译」**。

**实际检查方法**：

```
1. 看 build/esp-idf/<component>/lib<name>.a 是否存在、多大   ← 它早就在了
2. 看应用代码有没有真的调用它                                ← 链接器会做死代码消除
```

实测数据（本项目）：

| 阶段 | 产物大小 |
|---|---|
| 接入前 | 825,264 B |
| 已编译但**未调用** | 825,264 B（`.a` 已生成，但没被链接进最终产物） |
| **真正调用后** | **1,611,280 B（+786,016 B）** |

> **结论：判断"组件是否生效"要看最终产物增量 + 代码里是否真的调用了，而不是看构建日志里有没有它的名字。**

## 六、复用配网组件时发现的「坑位清单」（顺带奉上）

调研过程中记下的、与具体组件无关的通用坑（做配网一定会遇到）：

| 坑 | 说明 | 对策 |
|---|---|---|
| 频段 | ESP32-S3 **只支持 2.4 GHz** | 配网页要提示用户别用 5G 网络 |
| 企业认证 | **不支持 WPA2-Enterprise**（校园/企业网） | 提前在文档里说明 |
| 隐藏 SSID | 扫描不到 | 必须能手输 SSID |
| 门户检测 | 各平台探测 URL 不同（Android `/generate_204` 等） | 别依赖自动跳转 |
| HTTPS | **DoH / HTTPS 拦不住** | **必须大字提示用户手输 `192.168.4.1`** |
| 开放热点 | SoftAP 默认无密码 | 建议加密码 |
| **无限重启变砖** | 存了 SSID 但连不上 + 代码里 `ESP.restart()` → 无限重启 | **失败计数 ≥3 → 清凭证回配网** |
| 重置入口 | 用户改网络后可能再也进不去配网 | **必须有**（设置内 + 开机长按某键 5 秒） |
| 多设备同热点 | 同型号设备热点重名 | 热点名带 MAC 后 4 位 |

> 最后一条「无限重启变砖」是我认为**唯一一个真正危险**的坑：
> 它会让设备变成一块砖，且用户完全无法自救。**留一个物理按键重置入口是底线。**

---

## 七、一句话总结

> **复用不是「拿来用」，而是「接管它的债务」。**
> 先查许可证（法律债）、再查架构可分性（改造成本）、再读源码搞清它自己会干什么（行为债）、
> 最后自己补上离线化丢掉的依赖（构建债）。
> 这四步都不做就直接抄——债不会消失，只会在你最忙的那天到期。
