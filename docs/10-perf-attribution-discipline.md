# 10 · 性能归因纪律：先分段量，再猜硬件

> 场景：ESP32-S3 相册，进页面卡顿、返回卡顿。连续两次优化，
> **两次都推翻了「AI 的直觉」**——而且推翻的方向出奇一致：
> 不是「那件事做得慢」，是「**那件事本来就不该做**」。

## 结论（TL;DR）

三条纪律，按价值排序：

1. **先埋点，不改逻辑。** 一轮埋点拿全事实，胜过五轮「猜—改—测」。
2. **分段计时，不要总时长。** 总时长只告诉你「慢」，分段告诉你「慢在哪一层」。
3. **归因优先级：先查「有没有做无用功」，再查「那件事本身快不快」。**

本案例两次优化的收益，**90% 来自第 3 条**：

| 优化 | 表面问题 | 真因 | 收益 |
|---|---|---|---|
| 首屏卡顿 | 「SD 卡读得慢」 | 无条件多扫了一遍**空的** flash 目录 | 353 → 131ms |
| 缩略图浮出慢 | 「解码太慢」 | 每张都在读 **366KB 主图**，而不是 5KB 缩略图 | 单张 230 → 15ms |

## 为什么第一条是「先埋点，不改逻辑」

优化卡顿时最诱人的做法是「先按直觉改一版，测一下有没有变快」。
这个做法有个致命缺陷：**测出来变快了，你也不知道是哪一处起的作用；
测出来没变快，你也不知道该往哪改。**

本项目的第一轮做法是：**只加计时，一行逻辑都不改**，一次跑完拿到完整分账。

```
[prof] album scan=256ms  (SD mistakes: open 4ms read 13ms 39 条)
                         (SD casual:   open 2ms read 14ms 41 条)
                         (flash mistakes: read 113ms 0 条)
                         (flash casual:   read 109ms 0 条)
```

四个数字立刻把 256ms 拆干净：**两个 flash 目录贡献 222ms，而它们是空的**。

> 关键心态：**埋点时不要有「我已经知道答案了」的自信。**
> 我当时的预测是「空目录 readdir 应该就几毫秒」——实测 **113ms**，
> 差了**两个数量级**。如果按预测去改，这一轮会完全走空。

## 案例 A：空目录 ≠ 便宜

### 事实

设备存储是 **SD 优先、flash 兜底**的二选一（`dada_storage_init()` 里就定了）。
但负责建索引的 `rescan()` 无条件把两个后端都追加进去——flash 那一侧从来没被启用过，
目录物理存在但是**空的**。

### 直觉为什么错

「空目录」在人的心理模型里 = 没有东西 = 开销可忽略。

在 FAT 上是另一回事：`opendir` + `readdir` 的开销与**目录里有多少文件无关**，
它要做的是「定位目录项所在簇 → 按簇链读满整块 → 解析全部条目」。
这与「有没有内容」几乎无关。而 flash 上的 FatFS 还叠了一层 SPIFFS/分区映射。

### 修法

让 roots 数组**按当前后端互斥填充**：

```c
const char *roots[2];
int rn = 0;
if (dada_storage_backend() == STORAGE_SD) roots[rn++] = sd_root;
else                                      roots[rn++] = flash_root;
```

结果：`scan 259 → 35ms`，首屏 `353 → 131ms`，缩略图总数 **n=80 不变**，
PSRAM 占用**不变**。**收益全部来自「不做无用功」，没有一行代码变快。**

> 附带一条通用经验：**「空的东西」在嵌入式存储上不便宜。**
> 判断开销要看「有没有访问这个介质」，不要看「访问到几个结果」。

## 案例 B：语义错位的布尔参数

### 症状

从大图返回相册要 336ms，而首次进相册只要 128ms。截图还发现有几格**花屏**。

### 第一直觉（错的）

「返回时 SD 卡读得慢，可能是随机读抖动。」

于是加了文件读的分段埋点：

```c
int64_t t_open = now();
int fd = open(path, O_RDONLY);
int64_t t_seek = now();
/* lseek + read 循环 */
int64_t t_end = now();
if (t_end - t_open > 50000) {          /* 只打慢的那几条，别刷屏 */
    printf("[alfs] %s n=%ld open=%lldms rd=%lldms\n", name, size, ...);
}
```

**埋点第一行就把前面的假设推翻了**：

```
[alfs] IMG_60.jpg  n=366153  open=10ms  rd=300ms  total=311ms
[alfs] IMG_52.jpg  n=716987  open=10ms  rd=595ms  total=606ms
```

- 读的不是 `IMG_60_thumb.jpg`（5KB），是 **`IMG_60.jpg` 主图（366KB）**
- `open` 只有 10ms，慢的是 `read`——**说明不是目录查找慢，是搬了不该搬的数据**

同一张照片的 sidecar 实测只要 **15ms**。**慢 20 倍，因为读错了文件。**

### 真因

```c
/* 本意：没有 sidecar 时才回退读主图 */
grid_cell_load(pc, idx, allow_full /* = true 时走 src_get，即直接读主图 */);
```

而分帧补解那里**每一格都传了 `allow_full = true`**：

```c
slot_bind(k, idx, /*allow_full=*/true, ...);   /* ← 每帧一次，全部走主图 */
```

`allow_full` 的语义是「**允许**回退」，实现成了「**优先**回退」。
首屏那 2 张走的是 `false`（快），之后补解的每一张都走 `true`（慢）——
所以现象是「首屏有图，然后一张张慢慢浮出来」，看起来像「解码慢」。

改成 **sidecar 优先、失败才回退**：

```c
if (!dada_album_src_get_thumb(tab, idx, &it)) {     /* 先试 5KB sidecar */
    if (!allow_full) return;
    if (!dada_album_src_get(tab, idx, &it)) return;  /* 再回退主图 */
}
```

**单张 230ms → 15ms（15 倍）**，返回耗时 336 → 126ms，与首屏持平。

### 补丁里藏着的第二个坑

`get_thumb()` 只填 `it.thumb`，**不填 `it.full`**。
于是原来那条「sidecar 解码失败 → 回退主图救一下」的补救分支失效了（`it.full` 是空的）。
必须在这个分支里**再取一次** `src_get`。

> 教训：**改一个「取数据的路径」时，要检查依赖它填充的所有字段。**
> 这类「字段半空」的 bug 不会报错，只会表现为「那张图偶发空白」。

## 反面清单：这轮试过但**不解决问题**的路

| 做法 | 为什么无效 |
|---|---|
| 加更多格子提前渲染 | 内部 RAM 被对象吃光，解码工作缓冲被挤进 PSRAM，单张从 15ms 劣化到 80ms |
| 调大「每帧解码预算」 | 单张成本 > 一帧（33ms），预算再大也是同一帧里卡住 |
| 把 SD 频率从 20MHz 提到 40MHz | 瓶颈不在带宽，在「读了 366KB 不该读的数据」 |
| 换更快的解码库 | 解码只占 19ms/35ms，换掉也救不回 300ms 的读盘 |

**共同点：它们都在优化「本来就不该走的那条路径」。**

## 三条纪律的具体形态

### 1. 先埋点，不改逻辑

- 埋点保留在代码里，但**只在异常时打印**（0 条目 / 单目录 ≥20ms / 单文件 ≥50ms），
  正常路径零日志、零干扰。
- 拿到分账之后再动手，且**一次只改一个变量**。

### 2. 分段计时

至少切成 `open` / `read` / 解码 三段。案例 B 就是靠 `open=10ms` 这一条
排除了「FAT 目录查找慢」的猜测。

> 呼应第 5 节的「日志要写成断言」：**打印变量值，不要打印结论。**
> `rd=300ms` 是断言，`读取较慢` 是叙述。前者能推翻假设，后者只能复述。

### 3. 归因优先级

```
慢 → ① 它做了不该做的事吗？（扫空目录 / 读大文件 / 重复解码）
    → ② 它该做的事，单价合理吗？（35ms 里 16ms 读 + 19ms 解）
    → ③ 换硬件/换库/换线程
```

**顺序颠倒的代价**：本项目如果在第 ③ 层动手（加缓存、加线程、换解码库），
花几天也拿不到「353→131」「230→15」这两个数量级的收益——
因为前两层各藏着一个「白做」的动作。

## 一个容易误判的收尾细节：基准点要选对

改完之后量内存，看到「比基准少了 108KB」，第一反应是泄漏。核对了才对：

| 时点 | PSRAM free |
|---|---|
| 进相册（首屏只解 2 张） | 6860KB |
| 滚 6 次后 | **6864KB**（比基准还多 4KB） |
| 再滚 6 次（池满 9 张） | 6756KB |

第三次少 108KB ≈ 3.5 张缩略图，是「解 2 张 vs 解满 9 张」的**正常差**，不是泄漏。
判据是**第二次读数**：free/alloc 平衡，说明搬运路径没有泄漏。

> **基准点选错，会把正常波动当成故障；基准点选对，才能真正看到泄漏曲线。**
