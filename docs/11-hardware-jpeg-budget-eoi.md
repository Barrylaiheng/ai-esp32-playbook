# 11 · 硬件 JPEG 的两个隐形预算：DMA 描述符与帧长不可信

> 场景：ESP32-S3 + OV5640 走 sensor 片上 JPEG 直出（2560×1920，491 万像素），
> 目标是零软件编码拿到高清照片。
> 两个坑都不是「相机坏了」，而是**驱动的记账单位和报告长度不可信**：
> 一个卡在内部 RAM 的描述符，一个卡在 1025 字节的校验窗口。

## 结论（TL;DR）

**① 内存预算的单位不是字节，是「驱动的记账单位」。**
PSRAM JPEG 模式下，驱动每 1024 字节要一个 `lldesc_t`（12 B）放在**内部 RAM**。
所以「PSRAM 还有 7MB」完全没有意义——先耗尽的永远是内部 RAM 的那 12KB。

**② 帧长不是内容长度，是「分配长度」。**
同一模式下上报的 `fb->len` = `节点数 × 1024`，是个偏大的整数。
实测一帧真实 **4107 B 被报成 7168 B**（多 3061 B 填充）。
驱动自带的 EOI 校验窗口只有 **1025 B** → 永远扫不到真结尾 → 整帧被丢。

两条合起来的表现都是「`fb_get` 超时」，而**看起来都像硬件问题**。

## 症状与误判

| 现象 | 第一直觉 | 实际 |
|---|---|---|
| `frame dma malloc failed` | PSRAM 不够 | 内部 RAM 描述符不够，PSRAM 反而富余 |
| `NO-EOI - end marker missing` | 传感器没在出图 / 时序错 | 校验窗口 1025B 比填充短，永远扫不到 |
| `fb_get` 超时 | 接线/时钟/PLL | 上面任一条把整帧丢了 |
| 想「提高画质」把 QS 调小 | 数字小 = 质量好 | 低于 6 **静默断流**，只收到 5~6KB 且不报错 |
| 某张照片 700KB，画质应该很好 | 文件大 = 清晰 | 有效 JPEG + 几百 KB 垃圾尾部 → 解码花屏 |

**误判的共同点**：这些失败都**不报原因**。分配失败被日志静音吞掉，
EOI 误判表现为超时，QS 断流表现为「帧没来」。三个都指向硬件，三个都不是硬件。

## 坑一：描述符比 PSRAM 更早成为瓶颈

PSRAM JPEG 模式下 `cam_hal` 为缓冲每 1024 字节分配一个 `lldesc_t`（12 B），
**全部在内部 RAM**。真机实测：

| 预算 | 节点数 | 描述符占用 | 结果 |
|---|---|---|---|
| 2404 KB（2560×1920） | 2404 | ~29 KB | ❌ `frame dma malloc failed` |
| 1540 KB（2048×1536） | 1540 | ~18 KB | ❌ 同上 |
| 942 KB（1600×1200） | 920 | ~11 KB | ✅ 通过 |

本机内部 RAM 最大空闲块实测 **12~27 KB** → 可控帧大小约 **600~700 KB**。
预算上限收到 **600 KB** 后，QSXGA 实测只用 **315 KB（53%）**，余量充足。

配套的一条：JPEG 模式**必须**开 `esp_camera_set_psram_mode(true)`。
不开时驱动要走「内部 RAM 16KB 连续缓冲中转」：

```
cam_hal: DMA buffer 16384 Byte malloc failed, the current largest free block: 15360 Byte
```

差 1 KB 就 init 失败。**同一块板子，开与不开是「能跑」和「初始化就死」的区别。**
但注意：这条只对 JPEG 打开，RGB565 取景链路保持关闭——那是已经验收过的路径，不冒这个险。

## 坑二：帧长来自填充，EOI 必须自己扫

`cam_hal.c:393` 在 PSRAM 模式下把帧长上报成 **`节点数 × 1024`**。
而 `cam_take()` 的 EOI 探针窗口是 `dma_node_buffer_size + 1` = **1025 B**（`cam_hal.c:139`）。
真 EOI 在填充之前 3000 多字节 → **扫不到 → 判 NO-EOI → 整帧丢弃**。

修法两步：

1. 钩子跳过驱动校验（`cam_dada_skip_eoi(true)`）；
2. 自己正向扫 `FF D9` 得精确长度，只把 `real` 字节交给上层。

```c
static size_t jpeg_trim_len(const uint8_t *b, size_t len)
{
    if (!b || len < 4) return 0;
    for (size_t i = 2; i + 1 < len; i++)
        if (b[i] == 0xFF && b[i + 1] == 0xD9) return i + 2;   /* 只认第一次命中 */
    return 0;                                                  /* 被截断 */
}
```

**🔴 必须从头往后扫，不能从尾往前。**
缓冲区是复用的，尾部可能残留**上一帧**的 `FF D9`；从后往前会切出一个
「长度对、内容是上一帧」的图——比报错更糟，因为它是静默的错图。
而 JPEG 熵编码里 `FF` 一律转义成 `FF 00`，数据段不可能出现裸 `FF D9`，
所以**第一次命中就是真结尾**。

### 这条修完之前写出的文件是坏的

早期版本把 `fb->len` 整块写盘（没做 trim），于是产生了「有效 JPEG 头 + 几百 KB 垃圾尾部」的文件。
表现：缩略图花屏、**点开大图同样花屏**（同一个解码器的两条路径都坏 = 数据坏，不是 UI 坏）。
识别特征：体积落在任何正常产物之外的区间（716 KB，而正常 5MP 是 254~295 KB）。

**判据很好用：如果两个互不相关的消费者都坏，就别再查消费者。**

## QS 的可用范围是「有下限」的

OV5640 的 `0x4407[5:0]`：**1 = 质量最好/文件最大，63 = 最差/最小**，
方向与软件编码器 `fmt2jpg(quality)`（82 = 高质量）**完全相反**。真机扫了一遍（2560×1920）：

| QS | 实际字节 | 结果 |
|---|---|---|
| 1 / 4 | — | ❌ 只收到 5~6 KB 就断流，无 EOI |
| **6** | 505~538 KB | ✅ 但占预算 84~90%，余量很薄 |
| 8 | 415 KB | ✅ |
| **12** | **315 KB** | ✅ 占 53%，**推荐钉死** |
| 24 | 167 KB | ✅ 画质下降明显 |

**「调到 1 拿最高画质」这条直觉会直接把功能拍死**，而且不报错。
凡是「数字越大越好」的直觉，遇到厂商寄存器都要先反过来想一遍。

## 铁律

- [ ] **算内存预算前，先问「驱动按什么单位记账」**——不是总容量，是元数据开销。
  本项目：PSRAM 7MB 富余，内部 RAM 12KB 才是真上限。
- [ ] **`buf_len` 在 DMA 模式下恒为记账单位的整数倍**，永远不信它等于内容长度。
  收到帧的第一件事是 `SOI` + 正向 `FF D9` 双校验，拿 `real` 再往上交。
- [ ] **驱动自带的校验逻辑可能对某些模式不成立**（窗口长度 < 填充长度），
  它的失败表现是「超时」而不是「校验失败」，会把人往硬件方向带。
- [ ] **静默失败优先级最高**：初始化阶段临时放开被静音的日志。
  本项目 `cam_hal` 日志为压运行时刷屏被设成 `NONE`，连「分配失败」一起吞了。
- [ ] **两个独立消费者都坏 → 数据坏**。别在 UI 层找原因。
- [ ] **写盘侧只校验字节数是不够的**：`fwrite` 长度正确 ≠ 内容是完整 JPEG。
  上游交来「长度对、内容残缺」的缓冲会静默落盘，直到用户点开才发现。

## 边界（诚实记录）

- 预算上限 600 KB 是**实测收敛值**，不是芯片规格；换板子/换驱动版本必须重测
  （内部 RAM 空闲块是板级变量）。
- QS 可用下限 6 是这颗 sensor 在这套 PLL 配置下的结果，不保证跨配置成立。
- 拍照清晰度另有一条独立的坑（**AE 未收敛 → 过曝爆噪**，同场景高频噪声 26.63 vs 1.11），
  与本文的预算/EOI 无关，别把两者混成一条因果链。
